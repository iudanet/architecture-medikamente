# Что улучшить: защита данных

## 1. Данные для защиты и способы защиты

Термины по уроку «Методы защиты данных»: токенизация и зануление — обфускация; маскирование бывает статическим, динамическим, детерминированным и недетерминированным.

| Данные | Тег | Шифрование | Обфускация / маскирование | Обезличивание |
|---|---|---|---|---|
| Диагнозы, анамнез, хронические заболевания, заключения | `PHI` | Полевое AES-256 в БД ЭМК, файлы в шифрованном хранилище | Динамическое маскирование для всех ролей, кроме лечащего врача; статическое в dev и тестах | Для аналитики только агрегаты по псевдониму |
| Результаты анализов | `PHI` | AES-256 at rest, mTLS при обмене с лабораторией | Лаборатория получает `sample_id` вместо ФИО (токенизация) | Агрегаты для BI |
| ФИО, дата рождения | `PII.Identity` | AES-256 at rest | Динамическое маскирование вне ресепшена и врача | Детерминированный псевдоним `patient_id`; дата рождения обобщается до возраста |
| Паспорт, СНИЛС, полис | `PII.Identity` | Полевое шифрование | Видны только последние 4 символа | Не попадают в аналитику |
| Телефон, email | `PII.Contact` | Полевое шифрование | Ресепшен видит `***-**-12`; сервис уведомлений получает токен | Удаляются |
| Адрес, место работы | `PII.Contact` | — | — | Не собираются (минимизация) |
| Договор, факт и сумма оплаты | `Financial` | AES-256 at rest | Наименование услуги в 1С и чеке обобщено | Агрегаты по услугам |
| Данные банковских карт | `Financial` | TLS до эквайера | Токенизация на стороне эквайера, в системе не хранятся | — |
| Кадровые данные сотрудников | `PII.Employee` | Шифрование БД и бэкапов 1С | Динамическое маскирование паспорта и СНИЛС (последние 4 символа) | Не попадают в аналитику |
| Учётные данные, ключи, токены | `Secret` | Vault / HSM | — | — |
| ТМЦ, закупки | `Internal` | Шифрование бэкапов | — | — |

## 2. Механизм тегирования

Внедрение по шагам урока «Управление данными и тегирование»:

1. **Идентификация.** DLP и сканер каталога находят ПДн в БД, хранилище файлов и почте по шаблонам: ФИО, паспорт, СНИЛС, телефон, диагнозы по МКБ-10.
2. **Политика тегов.** Классы: `PHI`, `PII` (родительский тег; подтеги наследуют его политики) — `PII.Identity`, `PII.Contact`, `PII.Employee`, `Financial`, `Secret`, `Internal`, `Public`. Стадии: `raw` → `verified` → `golden`. Правила обработки: `Encrypt.Field`, `Mask.Dynamic`, `Pseudonymize`, `Retention.<срок>`, `Consent.Required`. Владелец тега — ответственный за обработку ПДн.
3. **Хранение и распространение.** Каталог данных — Apache Atlas: теги на БД, таблицах, колонках, файлах и потоках NiFi. Теги наследуются по lineage: колонка с `PHI` передаёт тег производным наборам.
4. **Контроль доступа по тегам.** Роли и атрибуты берутся из Keycloak, ABAC — «лечащий врач пациента».
   - В озере данных Apache Ranger применяет tag-based политики: отказ в доступе, динамическое маскирование, фильтрацию строк.
   - В PostgreSQL и ClickHouse используются нативные роли и row-level политики, маскирование выполняется в приложении по тегам из Atlas.
5. **Автоматическая проверка релиза.** В CI каждая миграция схемы и каждый API-контракт проверяются на наличие тегов у новых полей. Поле с `PHI`/`PII` без правила `Encrypt.Field`/`Mask.Dynamic` или без тега блокирует релиз. Результат проверки отправляется в VictoriaMetrics, алерт — в Grafana.
6. **Мониторинг и обновление.** Регулярное сканирование ищет неразмеченные ПДн (алерт). Ежеквартально проводится ревизия тегов. Теги-триггеры запускают удаление по `Retention` и архивирование.

## 3. Инструменты, способы и меры по потокам

| Поток (DFD) | Меры |
|---|---|
| Пациент → портал / приложение → CRM | TLS 1.3, OIDC + MFA (Keycloak); согласие на обработку и отдельное на медданные (сервис согласий); минимальный набор полей; полевое шифрование контактов |
| Ресепшен → портал ресепшена | RBAC «Ресепшен», динамическое маскирование контактов, медданные недоступны, аудит чтения |
| Врач → МИС / ЭМК | ABAC «лечащий врач», MFA, шифрование AES-256 + ключи в Vault/HSM, аудит каждого чтения → SIEM/UEBA |
| МИС ↔ лаборатория | API Gateway, mTLS, OAuth2 client credentials, контракт без ПДн (`sample_id`), договор поручения |
| Пациент → свои данные в приложении | Проверка владельца (`patient_id` из токена) на API Gateway; ответ фильтруется по тегам |
| Касса → платёжный шлюз → 1С | Токенизация карт у эквайера, интеграция с 1С по API и TLS, Excel-учёт отменён |
| Бухгалтерия → банк, ФНС, СФР | Банк: ДБО (1С:ДиректБанк) с ЭП; ФНС, СФР: ЭДО с ГОСТ-шифрованием (КриптоПро CSP); 1С в клиент-серверном режиме, доступ по группе AD |
| Источники → аналитика | Apache NiFi: TLS, псевдонимизация при загрузке; аналитик видит только `golden` ([Task2](../Task2/README.md#аналитический-слой)) |
| Все потоки | DLP на почте и рабочих станциях, запрет съёмных носителей, журнал доступа в Elastic, SIEM/UEBA для нетипичных действий, удаление по сроку и по запросу субъекта |

Меры для каждого этапа отмечены на страницах To-Be диаграмм ([README](./README.md)).
